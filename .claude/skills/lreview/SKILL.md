# lreview — 리뷰·검증·개선 루프

`../rreview/SKILL.md`의 리뷰·검증을 라운드마다 반복하고 권장안을 적용한다. 수용할 지적이 없을 때까지 라운드를 반복하고, 최대 라운드에도 권장안이 남으면 「복구」로 다시 구현한다. lreview 호출은 「복구」의 초기화와 세부 단계 커밋을 허락한 것으로 본다.

## 인자·준비

rreview의 「인자」·「준비」를 따른다.

- 실행 디렉터리는 `tmp/lreview/<yyyyMMdd-HHmmss>`다.
- 시작할 때 untracked 파일 목록을 기준 목록으로 `ledger.md`에 기록한다. 호출자가 목록을 넘기면 그것을 쓴다.
- 리뷰어는 라운드마다 같은 구성으로 새로 띄운다.
- 요청 범위가 바뀌면 `brief.md`를 갱신한다.

## 라운드

최대 10라운드. 라운드 N마다 아래를 순서대로 수행한다.

### 1. 리뷰·검증

rreview의 「리뷰」를 수행한다. 결과 디렉터리는 `<실행 디렉터리>/round-N`이다.

- 실패한 리뷰어가 있는 라운드는 "수용할 지적 없음" 종료의 근거로 쓰지 않는다. 같은 구성으로 라운드를 다시 실행하며, 다시 실행한 라운드도 최대 라운드 수에 포함한다.
- 같은 리뷰어가 같은 원인으로 두 라운드 연속 실패하거나 마지막 라운드에 실패한 리뷰어가 있으면 중단한다.
- 검증할 때 실행 디렉터리의 `ledger.md`(이전 라운드 기록)를 함께 본다. 이전에 기각한 지적이 다시 나오면 앞선 근거를 인용해 기각한다. 이전 라운드 수정이 만든 코드를 다시 지적하면 vreview의 「재설계 후 적용」 조건으로 판단한다.
- rreview 3·4의 정리와 보고서를 출력한 다음, vreview 보고서를 `round-N/vreview.md`에 저장하고 권장안을 적용한다. 파일 저장으로 출력을 대신하지 않는다.

### 2. 판정과 적용

| 조건                                                   | 처리                                      |
| ------------------------------------------------------ | ----------------------------------------- |
| 수용·일부 수용 항목이 없거나 권장 액션이 모두 「유예」 | 종료                                      |
| 수용 항목이 creview의 Nit뿐                            | 적용하고 종료(재리뷰하지 않음)            |
| 그 외, 마지막 라운드                                   | 적용하지 않고 실패. 「복구」를 따른다     |
| 그 외                                                  | 종합 권장 액션대로 적용하고 다음 라운드로 |

- sreview 지적은 심각도가 없으므로 Nit으로 보지 않는다.
- 「통합 후 적용」이면 개별 패치 대신 그룹 수정 하나로 적용한다.
- 「재설계 후 적용」이면 현재 상태에서 제시한 경계대로 다시 설계해 구현한다.
- 적용할 때 변경 파일에 해당하는 저장소 규칙을 따른다. 빌드·테스트는 사용자가 이번 호출이나 대화에서 명시적으로 허락한 범위에서만 하며, 호출자가 전달한 검증 지시·허락도 따른다. `git add -N` 외의 stage와 commit은 「복구」의 세부 단계 커밋에서만 한다.
- `ledger.md`에 라운드 기록을 덧붙인다: 지적 요약(리뷰어, `파일:라인`), 판정, 적용 여부, 수정한 파일.

## 복구

마지막 라운드에 권장안이 남으면 수행한다. 구현 실패로 복구를 요청받으면 「인자·준비」 뒤 라운드 없이 수행하며, 변경이 없다고 종료하지 않는다. 복구의 세부 단계에서 실패했으면 수행하지 않는다.

초기화: 플랜 파일이 있으면 실행 디렉터리에 백업하고 `git reset --hard <대상 커밋>`한 뒤, 기준 목록에 없던 untracked 파일을 실행 디렉터리 밖에서 지우고 플랜을 복원한다.

1. tracked 변경에 이번 작업이 아닌 것이 섞여 있으면 중단한다. 초기화하면 함께 지워진다.
2. `git diff HEAD --binary`를 `attempt.patch`로 저장하고 시작 커밋(`git rev-parse HEAD`)을 `ledger.md`에 기록한 뒤 시작 커밋으로 초기화한다.
3. brief·`attempt.patch`·`ledger.md`·검증 결과로 실패 원인을 분석해 현재 미완료 작업을 세부 단계로 나눈다.
   - 리뷰 집중 영역이 플랜 파일의 단계이면 그 아래에 `### N-1.` 형식으로 쓰되 기존 번호 뒤에 이어 쓴다. 아니면 실행 디렉터리의 `plan.md`에 쓴다.
   - 완료 기록은 보존하고 미완료 항목만 옮긴다. brief의 새 수정 작업은 미체크 항목으로 추가한다.
   - 단계마다 체크 항목과 완료 조건을 두고, 이전 라운드에서 수용한 지적을 해당 단계의 완료 조건에 넣는다.
   - `attempt.patch`는 문제없던 부분만 참고하고 통째로 적용하지 않는다.
4. 세부 단계마다 구현하고(새 파일은 `git add -N`) 허락된 단계 관련 검증을 통과한 뒤 「라운드」를 수행한다. 변경이 없으면 라운드 없이 통과한다. 라운드 수는 세부 단계마다 새로 센다.
   - 리뷰 집중 영역은 플랜 경로와 현재 세부 단계이고, 결과 디렉터리는 `step-<번호>/round-N`이다. brief에 세부 단계의 체크 항목·완료 조건과 이후 단계로 미룬 범위를 쓴다.
   - 통과: 체크 항목을 `[x]`로 바꾸고, 세부 단계에서 바꾼 tracked 파일만 stage해 `../commit/SKILL.md`의 메시지 규칙으로 커밋한다. tracked 변경이 없으면 커밋을 건너뛴다.
   - 실패(완료 조건 미충족, 같은 원인으로 세 번 고쳐도 검증 실패, 라운드 실패): 변경을 `step-<번호>.patch`로 저장하고 직전 커밋으로 초기화한다. 그 세부 단계를 다시 나눠 플랜에 쓰고 이어서 구현한다. 원래 작업 기준으로 두 번 나눈 뒤에도 실패하면 중단한다.
   - 환경 오류면 중단한다.
5. 중단해도 통과한 세부 단계의 커밋은 남긴다.

## 최종 보고

- 진행한 라운드 수와 종료 사유
- 라운드별 실행 리뷰어(실패 포함), 수용·기각 수, 적용한 수정
- 남은 항목: 보류·유예, 적용하지 않은 권장안, 재리뷰를 거치지 않은 마지막 수정
- 복구했으면: 시작 커밋, 플랜 경로, 세부 단계와 나눈 이유, 단계별 커밋, `attempt.patch`·실패 patch 경로
- 수행하지 않은 검증(빌드·테스트)
- 실행 디렉터리 경로
