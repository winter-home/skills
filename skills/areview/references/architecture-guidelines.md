# 아키텍처·구조 설계 리뷰 기준

## 구조 추적

1. 프로젝트 문서·디렉터리·주요 진입점을 살펴 변경이 속한 기능 영역·계층·실행 단위와 그 의존 관계를 파악한다. 먼저 상위 구조와 변경의 위치를 짧게 정리한다.
2. 변경된 기능의 대표 업무 흐름을 따라 관련 경계의 호출·데이터·상태·외부 효과를 추적한다. 공개 계약·변경 전후 구현·테스트를 대조해 정상 처리부터 오류·취소·복구까지 책임이 어떻게 전달되는지 확인한다.
3. 아래 관점으로 변경이 여러 기능·계층에 미치는 구조적 영향을 평가한다. 범위가 넓으면 주요 업무 흐름·공유 경계·변경 집중 영역을 우선하며, 실제로 깊게 검토한 범위와 남은 범위를 보고한다.

## 검토 관점

- **업무 책임·정책 배치:** 기능 영역의 구분과 UI·API·배치·저장소·외부 연동 사이의 책임 배치가 일관적인가? 같은 업무 규칙이 여러 경로에 흩어져 각각 관리되는가?
- **계층·하위 시스템의 의존 관계:** 핵심 정책이 특정 프레임워크·DB·외부 서비스의 구현 세부사항에 묶이는가? 순환 의존·내부 표현 노출로 경계 간 변경이 과도하게 전파되는가?
- **데이터·상태 소유권:** 공유 데이터의 기준 정보와 갱신 책임이 분명한가? 경계를 넘는 상태·자원 수명과 트랜잭션·오류·취소·복구 책임이 연결돼 정합성을 유지하는가?
- **변경·실행·검증의 경계:** 하나의 업무 정책 변경이 무관한 영역의 동시 수정을 요구하는가? 전역 상태·공유 설정·강한 결합이 요구되는 독립 실행·배포·검증을 방해하는가?

## 판단과 보고

- 변경으로 새로 생기거나 악화된 구조 문제만 지적한다. 기존 구조는 비교·영향 분석의 근거로 사용하며, 변경과 무관한 기존 문제는 제외한다.
- 실제 의존 관계·호출 경로 또는 확정된 후속 요구사항으로 영향을 설명한다. 버그가 없어도 근거 있는 구조 문제를 검토하되, 가상의 확장·설계 원칙 이름·파일 크기만으로 문제를 단정하지 않는다.
- 함수·클래스 단위의 정리보다 여러 영역에 영향을 주는 책임 배치와 경계 문제를 우선한다. 파일 분리·클래스 추가·디자인 패턴 도입 자체를 개선으로 보지 않는다. 제거·통합·기존 경로 활용을 포함해 입증된 문제 해결에 필요한 범위의 구조 조정을 제안한다.
- 한국어로 현재 구조와 검토 범위를 먼저 요약한다. 각 지적은 `문제 구조 → 구체적인 유지보수·변경 영향 → 권장 구조 → 유지할 동작·공개 계약·오류 처리·검증 강도` 순서로 설명하고 관련 파일·라인을 근거로 첨부한다. 여러 기능·파일에 걸친 같은 원인은 하나로 묶는다.
- **필수 개선**과 **선택적 개선**을 구분한다. 필수 개선은 현재·확정된 요구사항이나 계약을 충족하지 못하거나 실제 구조에서 구체적인 정합성·변경 누락 위험이 확인된 경우다. 동작은 충족하지만 유지보수 비용을 줄일 수 있는 대안은 선택적 개선으로 적는다.
- 근거가 부족한 중요한 사항은 확인 필요 항목으로 분리한다. 지적할 내용이 없으면 명시하고, 검토하지 못한 중요한 경계와 검증 한계를 함께 보고한다. 항목 수를 채우거나 설계를 점수화하지 않는다.
