# 커밋

tracked 파일의 변경 사항을 분석하여 프로젝트 커밋 메시지 규칙에 맞게 커밋한다.

## 인자

- 호출 인자(`$ARGUMENTS`)의 첫 항목이 `KEY-숫자` 형식(예: `JIRA-1234`)이면 지라 티켓 번호로 사용하고, 나머지는 참고사항으로 해석한다.
- 첫 항목이 티켓 형식이 아니면 전체를 참고사항으로 해석한다. 참고사항만 있거나 인자가 없으면 티켓 번호를 붙이지 않는다.
- 참고사항의 파일 한정·제외 지시를 커밋 대상 선정에 우선 반영한다. 이미 staged된 파일도 이 지시를 따르며, 제외할 변경은 작업 트리에 보존한다.

## 동적 컨텍스트

### 현재 상태

!`git status 2>/dev/null`

### Staged diff

!`git diff --staged 2>/dev/null`

### Unstaged diff (tracked only)

!`git diff 2>/dev/null`

## 커밋 대상

- **포함**: staged 또는 tracked 파일의 변경분 (added / deleted / modified / renamed)
- **제외**: untracked(`??`) 파일은 절대 `git add` 하지 않는다

## 커밋 메시지 규칙

### 형식

```
1행: 타이틀
2행: (빈 줄)
3행~: 변경 설명
```

### 타이틀 (1행)

- **지라 번호 있음:** `<티켓 번호> [대분류] 타이틀 메시지`
- **지라 번호 없음:** `[대분류] 타이틀 메시지`

`[대분류]`는 변경 내용의 기능 영역이다.

타이틀은 **무엇을 했는지** 명확하게 표현한다. 동적 컨텍스트의 최근 커밋 스타일과 일관성을 유지한다.

### 본문 (3행~)

변경 사항에 대한 간략한 설명을 작성한다.

- diff에서 드러나지 않는 **왜**(의도, 맥락, 판단 근거)를 설명한다.
- 무엇을 변경했는지 나열하는 것이 아니라, 왜 이 변경이 필요한지를 쓴다.
- 한 줄로 충분하면 한 줄만 쓴다. 단순한 변경에 장황한 본문은 불필요하다.

## 절차

### 1단계: 변경 분석

동적 컨텍스트에서 변경 파일과 diff를 파악한다.

- 변경이 없으면 **"변경 사항 없음"**을 보고하고 즉시 종료한다.

### 2단계: 사전 검증

커밋 전 아래 항목을 확인한다.

- **시크릿 포함 여부**: diff에 비밀번호, API 키, 토큰, 인증 정보가 포함되어 있으면 경고하고 해당 파일을 커밋하지 않는다.
- **untracked 파일 혼입**: `git status`에 `??`인 파일이 있어도 무시한다. 절대 `git add`하지 않는다.
- **의도하지 않은 변경**: diff에 작업과 무관한 변경(디버그 코드, 임시 수정)이 포함되어 있으면 사용자에게 알린다.

### 3단계: 스테이징 및 커밋

1. 커밋에 포함할 파일만 명시적으로 `git add <파일명>` (절대 `git add .`이나 `git add -A` 사용 금지)
2. 커밋 메시지를 작성한다 (커밋 메시지 규칙 준수, 최근 커밋 스타일 참조)
3. `git commit` 실행

### 4단계: 결과 보고

- `git log --oneline -5`로 커밋 결과를 확인하여 사용자에게 보고한다.

## 흔한 합리화

| 합리화                               | 현실                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| "git add . 이 편하다"                | untracked 파일, 시크릿, 빌드 산출물이 함께 커밋될 수 있다. 파일명을 명시적으로 지정한다.                    |
| "커밋 메시지는 나중에 정리하면 된다" | 나중은 오지 않는다. 커밋 메시지는 작성 시점에 정보가 가장 풍부하다. 지금 제대로 쓴다.                       |
| "본문까지 쓸 필요 있나"              | 타이틀만으로 의도가 드러나지 않는 변경은 본문이 필요하다. 다만 단순한 변경에 장황한 본문은 오히려 노이즈다. |

## 레드 플래그

- `git add .` 또는 `git add -A` 사용
- untracked 파일을 `git add`에 포함
- diff에 시크릿(비밀번호, 토큰, 키)이 포함된 채 커밋
- 최근 커밋 스타일을 확인하지 않고 독자적 형식 사용
- 커밋 메시지 타이틀이 변경 내용을 반영하지 않음

## 검증 체크리스트

커밋 후 확인한다:

- [ ] untracked 파일이 커밋에 포함되지 않았는가
- [ ] 시크릿이 diff에 포함되지 않았는가
- [ ] 티켓 번호 유무에 맞는 타이틀 형식을 따르는가
- [ ] `git log`로 커밋 결과를 확인했는가
