# lwork — 리뷰·검증·개선 루프

`../pwork/SKILL.md`의 리뷰·검증과 권장안 적용을 「판정과 적용」의 종료 조건까지 반복한다. 「판정과 적용」에서 실패로 판정하면 일반 라운드는 「복구」, 복구 중에는 「세부 단계 실패」로 이동한다. lwork 호출은 단독 실행의 성공 커밋과 「복구」의 초기화·세부 단계 커밋을 허락한 것으로 본다.

## 인자·진입 경로

첫 인자가 `KEY-숫자` 형식(예: `JIRA-1234`)이면 지라 번호로 분리하고, 나머지 인자는 `../pwork/SKILL.md`의 「인자」를 따른다. 생략하면 번호를 붙이지 않는다. 번호가 있으면 일반 성공·복구의 모든 커밋에서 `../commit/SKILL.md`의 첫 인자로 넘기며, 재분할에도 유지한다.

호출자는 작업 맥락(플랜 경로·단계), 구현 실패 여부, untracked 기준 목록, 검증 지시·허락 범위, 일반 성공 커밋 담당(기본 lwork)을 함께 넘길 수 있다. 복구의 세부 단계 커밋은 이 지정과 관계없이 lwork가 수행한다.

| 요청 | 준비 후 이동 |
| ---- | ------------ |
| 일반 리뷰 | 「라운드」. 변경이 없으면 종료 |
| 구현 실패 | 변경 유무와 관계없이 「복구」 |

## 준비

1. 호출자가 넘긴 untracked 기준 목록을 쓰고, 없으면 새 파일을 `git add -N` 하기 전에 현재 목록을 확보한다.
2. pwork의 「준비」를 따르되 실행 디렉터리는 `tmp/lwork/<yyyyMMdd-HHmmss>`로 하고, 지라 번호(없으면 없음)와 기준 목록을 `ledger.md`에 기록한다. 구현 실패 요청에는 변경이 없을 때의 종료 규칙을 적용하지 않는다.

- 리뷰어는 라운드마다 같은 구성으로 새로 띄운다.
- 요청 범위가 바뀌면 `brief.md`를 갱신한다.
- 이전 라운드의 결과·`ledger.md`·`vreview.md`는 리뷰어에게 전달하지 않고 메인 에이전트의 검증·복구에만 사용한다.

## 구현 결과 확인

빌드·테스트는 사용자가 이번 호출·대화에서 명시적으로 허락한 범위와 호출자의 검증 지시·허락을 따른다. 구현 결과·완료 조건 확인에 실패하면 현재 작업에서 원인을 고쳐 다시 확인한다. 실패 자체나 같은 원인의 지적·수정 반복 횟수만으로 복구·재분할하지 않는다.

환경 오류로 필수 검증을 완료할 수 없고 대체 수단도 없으면 중단한다. 선택적 추가 검증의 환경 제약은 보고하고 계속한다. 구현상 이유로 완료 조건을 충족할 수 없다고 판단하면 일반 라운드에서는 「복구」, 복구 중에는 「세부 단계 실패」로 이동한다. 수정 후에도 이 절을 수행하고, 필수 검증을 통과한 뒤 리뷰·완료 처리를 이어 간다.

## 라운드

최대 5라운드. 라운드 N마다 아래를 순서대로 수행한다.

### 1. 리뷰·검증

pwork의 「리뷰」를 수행한다. 기본 결과 디렉터리는 `<실행 디렉터리>/round-N`이며, 복구 중에는 「세부 단계 실행」의 경로를 쓴다. 리뷰어 실패는 아래 규칙으로 처리한다.

- 실패한 리뷰어가 있는 라운드는 "수용할 지적 없음" 종료의 근거로 쓰지 않는다. 같은 구성으로 라운드를 다시 실행하며, 다시 실행한 라운드도 최대 라운드 수에 포함한다.
- 같은 리뷰어가 같은 원인으로 두 라운드 연속 실패하거나 마지막 라운드에 실패한 리뷰어가 있으면 중단한다.
- 검증할 때 실행 디렉터리의 `ledger.md`(이전 라운드 기록)를 함께 본다. 이전에 기각한 지적이 다시 나오면 앞선 근거를 인용해 기각한다. 이전 라운드 수정이 만든 코드를 다시 지적하면 vreview의 「재설계 후 적용」 조건으로 판단한다.
- pwork의 「지적 정리」·「검증」 결과를 출력하고, vreview 보고서를 해당 라운드의 `vreview.md`에 저장한다. 파일 저장으로 출력을 대신하지 않으며, 적용 여부는 「판정과 적용」에서 결정한다.

### 2. 판정과 적용

리뷰어 실패 처리를 마친 뒤, vreview에서 수용·일부 수용한 항목 중 「유예」를 제외한 항목을 기준으로 아래 표를 위에서부터 적용한다.

| 조건                                                   | 처리                                      |
| ------------------------------------------------------ | ----------------------------------------- |
| 남은 항목 없음                                         | 성공 종료                                 |
| 마지막 라운드에 간결성 개선·areview의 선택적 개선·creview의 Nit만 남음(혼합 포함) | 적용하지 않고 미적용 권고로 보고한 뒤 성공 종료(복구 중 세부 단계도 통과) |
| 그 외, 마지막 라운드                                   | 적용하지 않고 실패. 일반 라운드면 「복구」, 복구 중이면 「세부 단계 실패」로 이동 |
| 그 외                                                  | 종합 권장 액션대로 적용하고 다음 라운드로 |

- 간결성 개선은 리뷰어 종류가 아닌 지적 내용으로 판단하며, 동작·계약·검증 강도를 유지하는 단순화 권고만 해당한다. 범위 이탈이나 버그, 명시적 요구사항·저장소 규칙 위반은 제외한다.
- areview의 선택적 개선은 vreview에서도 선택적이라고 확인한 항목만 해당한다. 필수 설계 개선은 기존 수정·복구 절차를 따른다.
- sreview·areview 지적은 creview의 Nit로 보지 않는다.
- Nit도 적용하면 다음 라운드에서 재리뷰한다.
- 「통합 후 적용」이면 개별 패치 대신 그룹 수정 하나로 적용한다.
- 「재설계 후 적용」이면 현재 상태에서 제시한 경계대로 다시 설계해 구현한다.
- 적용할 때 변경 파일에 해당하는 저장소 규칙을 따르고 「구현 결과 확인」을 수행한다. `git add -N` 외의 stage와 commit은 「성공 후 처리」와 「복구」의 세부 단계 커밋에서만 한다.
- `ledger.md`에 라운드 기록을 덧붙인다: 지적 요약(리뷰어, `파일:라인`), 판정, 적용 여부, 수정한 파일.

## 복구

「구현 결과 확인」·「판정과 적용」에서 이 절로 이동했거나 구현 실패 요청을 받으면 수행한다. 복구 중 세부 단계가 실패하면 복구를 처음부터 다시 시작하지 않고 「세부 단계 실패」를 따른다.

최초 분할·재분할 모두 수용한 지적을 충족해야 할 동작·계약으로 바꿔 완료 조건에 반영한다. 플랜과 brief에는 리뷰 출처·판정·수정 이력을 넣지 않는다.

### 복구 준비

1. tracked 변경에 이번 작업이 아닌 것이 섞여 있으면 중단한다. 초기화하면 함께 지워진다.
2. `git diff HEAD --binary`를 `attempt.patch`로 저장하고 시작 커밋(`git rev-parse HEAD`)을 `ledger.md`에 기록한다.
3. 「초기화」 절차로 시작 커밋에 되돌린다.
4. brief·`attempt.patch`·`ledger.md`·검증 결과로 실패 원인을 분석해 현재 미완료 작업을 세부 단계로 나눈다.
   - 작업 맥락에 플랜 경로·단계가 있으면 그 아래에 `### N-1.` 형식으로 쓰되 기존 번호 뒤에 이어 쓴다. 아니면 실행 디렉터리의 `plan.md`에 쓴다.
   - 완료 기록은 보존하고 미완료 항목만 옮긴다. brief의 새 수정 작업은 미체크 항목으로 추가한다.
   - 단계마다 체크 항목과 완료 조건을 둔다.
   - `attempt.patch`는 문제없던 부분만 참고하고 통째로 적용하지 않는다.

### 세부 단계 실행

세부 단계마다 아래를 수행한다. 실패 처리는 「세부 단계 실패」를 따른다.

1. 작업 맥락을 플랜 경로·현재 세부 단계로 갱신한다. brief는 pwork의 「brief 원칙」에 따라 해당 원문 위치·검토 범위를 적고 이후 단계로 미룬 범위를 구분한다.
2. 구현하고(새 파일은 `git add -N`) 「구현 결과 확인」을 수행한다.
3. 변경이 없으면 라운드 없이 통과한다. 있으면 「라운드」를 수행한다. 라운드 수는 세부 단계마다 새로 세고 결과 디렉터리는 `step-<번호>/round-N`이다.
4. 통과하면 체크 항목을 `[x]`로 바꾸고, 세부 단계에서 바꾼 tracked 파일만 stage해 `../commit/SKILL.md`의 메시지 규칙으로 커밋한다. tracked 변경이 없으면 커밋을 건너뛴다.

모든 세부 단계가 통과하면 복구를 마친다. 중단해도 통과한 세부 단계의 커밋은 남긴다.

### 세부 단계 실패

- 「구현 결과 확인」의 환경 오류 중단 조건에 해당하거나 리뷰어 실행 실패로 라운드가 중단되면 중단한다.
- 「구현 결과 확인」 또는 마지막 라운드에서 이 절로 이동했으면 변경을 `step-<번호>.patch`로 저장하고 「초기화」로 직전 커밋에 되돌린다.
- 원래 작업 기준으로 두 번 나눈 뒤에도 실패하면 중단한다. 그 전에는 실패한 세부 단계를 다시 나눠 플랜에 쓰고 「세부 단계 실행」을 이어 간다.

### 초기화

「복구 준비」·「세부 단계 실패」에서 지정한 대상 커밋으로 되돌릴 때만 수행한다.

1. 플랜 파일이 있으면 실행 디렉터리에 백업한다.
2. `git reset --hard <대상 커밋>`으로 되돌린다.
3. 기준 목록에 없던 untracked 파일을 실행 디렉터리 밖에서 지운다.
4. 백업한 플랜을 복원한다.

## 성공 후 처리

일반 라운드가 성공 종료하거나 복구 전체가 통과하면 수행한다. 복구 중 개별 세부 단계는 「세부 단계 실행」의 커밋 절차로 돌아간다.

- 일반 성공 커밋 담당이 lwork이면 이번 작업에서 검토·수정한 tracked 파일만 대상으로 `../commit/SKILL.md`를 읽고 커밋한다. 대상 파일 한정·제외 사항을 함께 넘기고 대상 외 변경은 보존한다.
- 호출자 담당이면 커밋하지 않고 성공 결과를 반환한다.
- 대상 변경이 없거나 복구에서 이미 커밋해 남은 변경이 없으면 커밋을 건너뛴다. 커밋 실패 시 오류를 보고하고 중단한다.

## 최종 보고

- 성공 커밋 해시 또는 커밋 생략 사유(변경 없음·호출자 담당)
- 진행한 라운드 수와 종료 사유
- 라운드별 실행 리뷰어(실패 포함), 수용·기각 수, 적용한 수정
- 남은 항목: 보류·유예, 적용하지 않은 권장안, 재리뷰를 거치지 않은 마지막 수정
- 복구했으면: 시작 커밋, 플랜 경로, 세부 단계와 나눈 이유, 단계별 커밋, `attempt.patch`·실패 patch 경로
- 수행하지 않은 검증(빌드·테스트)
- 실행 디렉터리 경로
