# mkplan — 단계별 구현 플랜 생성

호출 인자(`$ARGUMENTS`)는 구현할 작업이다. 비어 있으면 작업 내용을 확인한 뒤 진행한다. 플랜 작성만 수행하며 구현·리뷰·커밋·푸시는 시작하지 않는다.

## 생성

1. 대상 프로젝트 루트와 저장소 규칙, 관련 코드·문서를 확인한다. Git 저장소이면 `git rev-parse --show-toplevel`을 쓰고, 아니면 작업 맥락에서 확인한 프로젝트 루트를 쓴다.
2. 사용자 요청·합의된 요구사항과 제안하는 구현 방법을 구분한다. 범위를 정하는 데 필수 정보가 없으면 확인하고, 미확정 사항을 확정된 요구사항으로 쓰지 않는다.
3. 아래 기준으로 단계를 나누고 선행 관계·작업 항목·완료 조건을 정한다. 기존 구현과 중복되는 작업은 피한다.
4. 사용자 시간대의 실제 현재 시각을 확인해 `yyyyMMddHHmm`으로 기록한다. 시간대를 알 수 없으면 시스템 로컬 시간을 쓴다. 프로젝트 루트의 `plans/`가 없으면 만든다.
5. `plans/{timestamp}_{작업명}.md`를 새로 만든다. 작업명은 요청을 나타내는 짧은 이름으로 정리하고 공백·파일명 금지 문자를 `-`로 치환하며 끝의 공백·마침표를 제거한다. 같은 경로가 있으면 작업명에 `-2`, `-3` 등을 붙여 빈 이름을 고르고 기존 파일은 덮어쓰지 않는다.
6. 아래 플랜 구성과 실행·갱신 규칙을 파일에 포함한다. 생성한 파일 경로, 단계 요약, 보류·미확정 사항을 보고한다.

## 단계 크기

- 한 번의 구현·관련 검증·리뷰·커밋으로 마칠 수 있는 하나의 변경 묶음으로 잡는다. 서로 다른 목표가 섞여 검증하기 어렵다면 나누고 같은 목표의 작은 수정은 묶는다.
- 파일·함수마다 기계적으로 나누거나 서로 독립적인 큰 기능을 한 단계에 몰지 않는다. 단계 수·파일 수·예상 시간에 획일적인 제한을 두지 않는다.

## 플랜 구성

- 제목과 목표·요구사항: 사용자 요청, 요구사항 원문 위치(있으면), 합의한 범위·제외 사항을 기록한다. 구현 방법은 조정 가능한 계획으로 구분한다.
- 실행·갱신 규칙: 아래 규칙을 포함해 후속 실행 에이전트가 같은 파일을 관리하도록 한다.
- 단계: `## 1단계. 제목`, `## 2단계. 제목` 순으로 작성한다. 각 단계에 목표, 선행 단계(없으면 없음), `- [ ]` 작업 항목, 확인 가능한 완료 조건을 둔다. 체크박스는 단계의 작업 항목에만 사용한다.
- 변경 기록: 최초 작성 시각과 이후 범위·단계·결정 변경의 사유·영향을 간결하게 남긴다.

## 플랜에 포함할 실행·갱신 규칙

- 실행 에이전트는 단계의 구현과 필요한 검증·리뷰를 통과한 뒤 해당 작업 항목을 `[x]`로 바꾼다. 보류를 제외한 항목이 모두 완료되고 완료 조건을 충족하면 해당 단계가 완료된 것이다. 보류가 남으면 그 사실을 함께 표시한다.
- 진행 중 확정된 범위·단계·결정 변경을 플랜 본문에 반영하고 변경 기록에 사유·영향을 남긴다. 사용자 요구사항은 임의로 바꾸지 않는다.
- 완료된 단계의 번호·체크·기록은 보존한다. 미완료 단계만 추가·분할·조정하며, 분할은 해당 단계 아래 `### N-1. 제목` 형식을 쓴다. 완료된 작업에 추가 작업이 생기면 새 항목·단계로 구분한다.
- 외부 자료·실기기·사용자 결정이 필요한 미해결 항목은 `- [ ] 보류: 사유`로 표시한다. 보류 항목의 해소가 선행 조건이면 의존 작업을 진행하지 않는다.
- 리뷰 지적·판정·수정 이력 등 실행 로그는 플랜에 넣지 않고 별도 실행 기록에 둔다. `implan`으로 실행하면 해당 스킬의 검증·완료·커밋 절차를 따른다.
